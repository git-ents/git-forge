# query is two disconnected surfaces: ad-hoc in-process scans that duplicate a real Datalog engine, and a Datalog engine nobody can discover how to address

**What**

`git-forge query` has six subcommands split across two unrelated
implementations. `run` reaches the real `gix-query` Datalog engine. `assignee`,
`reviewer`, `requester`, `keyword` and `find` do not touch it at all -- they
load every entity in the repository and filter in a Rust loop.

**Where**

- `crates/git-forge/src/main.rs:663` to `:785` -- the hand-rolled scans
- `crates/git-forge/src/main.rs:638` -- `Run`, the only real query path
- `crates/gix-forge/src/lib.rs:266` -- `query_goal` / `query_predicate`

**Three concrete consequences**

First, the sugar is a worse engine sitting next to a better one. `query find`
does not compose: pass `--assignee` and every review is skipped
(`main.rs:762`); pass `--reviewer` and every issue is skipped
(`main.rs:747`). Those are hardcoded `continue` statements standing in for a
join that Datalog would do properly.

Second, it is wrong. `query keyword` has a `visible_alias = "title"`
(`main.rs:145`) but searches only `issue.body`:

    git-forge query title Markdown
    matches for "Markdown":
      (none)

The issue titled `Markdown round trip` is not found by
`query title Markdown`. It is found by `query title Heading`, because Heading
is in its body. The alias says one thing and the code does another.

Third, the real engine is undiscoverable. Rule-module predicates must be
addressed with a module prefix, and nothing says so:

    git-forge query run --goal "reviewed(B)" --select B
    Error: reviewed/1 in the goal is not defined

    git-forge query run --goal "review.reviewed(B)" --select B
    query results:
      (none)

There is no `query predicates` or `--list` to find out what is askable, no help
text on `run`, and the error message names the problem without naming the fix.

**Why it matters**

`query` is where `git-forge` composes with a sibling, so it is carrying a
disproportionate share of the four-project story. Right now the part that
composes is hidden behind an unexplained naming convention, and the part that
is discoverable is a reimplementation that duplicates the engine badly. A
viewer who tries `query find` concludes the query story is thin; a viewer who
tries `query run` cannot get a predicate name right on the first attempt.

The full-scan implementation is also the wrong asymptotics on purpose:
`known_issue_values` and every sugar subcommand load every entity from disk on
every invocation. Invisible at eight issues, quadratic-feeling at a few
thousand.

**Options**

- Option A -- Delete the sugar and make `find` a Datalog goal builder that
  emits a query against forge-backed host predicates. Trade-off: depends on
  those host predicates existing, which is the separate integration issue.
- Option B -- Keep the sugar as a thin convenience but implement it in terms of
  `query_predicate` so there is one evaluator. Trade-off: needs forge facts
  exposed to `gix-query` first.
- Option C -- Leave the two surfaces separate but fix the visible faults: make
  `title` search titles, make `find` filters compose, add `query predicates` to
  list what is askable, and document the module prefix in `run --help`.
  Trade-off: cheap and honest, but keeps two evaluators forever.

**Recommendation**

C before the talk, A after. High confidence on the `title` bug and the
discoverability gap -- those are unambiguous. The A-versus-C choice is a real
judgement call about scope, but I would not demo `query find` in its current
state: the hardcoded skips are visible the moment anyone combines two flags.
