== Governing principle

The family's contract is the on-disk format — published schemas, ref layout, claim trailers — never crate imports.
The four repositories read better as five layers than as four peers:

[cols="1,2,3", options="header"]
|===
| Layer | Lives in | Contract

| Encoding | `facet-git-tree` | Values to trees and back, including verbatim oid passthrough: `RawTree` exists (`ser.rs:105-110`); its blob analogue `RawBlob` does not yet.
| Typed state | `git-store` | Kinds, schema binding, ref layout, `put_schema`.
| Attachment primitives | `git-anchor` and the claim format under `refs/meta/claims/*` | Positioned annotation and signed assertion.
| Query | `git-query` | Datalog over the ref layout; the claims vocabulary is already implemented in `gix-query-host`.
| Vocabulary | `git-forge` | Issues and reviews — the first product built on all the layers below it, not a fourth peer.
|===

The layering is closer to real than the review first credited.
`git-anchor` already encodes through `facet_git_tree::serialize_into` (`store.rs:256`), so the encoding layer is genuinely shared; what it bypasses is `git-store`'s schema and ref layer, and no product except `git-forge` calls `put_schema`.
The diagnosis is narrow: shared encoding, unpublished contracts.
The rule that follows: every product publishes the schema of what it stores, and products compose by reading each other's published formats, never by importing each other's crates.

== Cross-cutting findings

Three patterns recur in all four repositories and account for most of the `visible` count.

=== The last three feet are missing

The hard half of each feature is built and unreachable.

* `git-query` has spanned diagnostics from nine validation passes that are rendered with `to_string()`, a derivation tree with reconstructed negation witnesses and no `explain` subcommand, and an exit code 3 documented normatively in two places with no producer.
* `git-anchor` has a `witnesses()` mechanism that makes the lossy fuzzy fallback unnecessary, with zero callers.
* `git-store` pins the exact schema commit each value validated against, then binds it with a text trailer.
* `git-forge` publishes a schema for `Issue` while storing `StoredIssue`.

Wiring something already implemented is the cheapest visible work available, and there is a lot of it.

=== Data does not travel

Three of four fail at a repository boundary.

[cols="1,3", options="header"]
|===
| Repository | Symptom

| `git-store`  | Fetching a data ref yields `object could not be found`; the schema is not reachable from the data commit.
| `git-forge`  | A fresh clone reports `No issues` with exit 0.
| `git-anchor` | No refspec, no fetch or push porcelain, no documentation.
|===

For a talk arguing Git is a distributed datastore, this is the question in the room.

=== The family does not compose — yet the receiving side is already built

`git-forge` reviews cannot affect a `git-query` policy answer today, but the gap is one write, not a missing subsystem.
`gix-query-host/claim.rs` already implements `claim/1`, `kind/2`, `target/2`, `signer/2`, and `verdict/2` off commit trailers under `refs/meta/claims/*`, and the reference vocabulary already joins reviews to anchors to line spans through `anchor/1`, `bind/7`, and `reviewed_span`.
`git-forge` simply never writes a claim.
No `verdict` field on `Review` is needed or wanted — the claim trailer carries `Verdict:` and the predicates read only trailers.
`git-anchor` pins comments to moving code while `git-forge` comments are a single overwritable edit-reason slot; the resolution is delegation, not parallel implementation (see After the conference).
Four projects on one stage that do not touch each other is a weaker story than three that do.

== Global unblocker

`git-store` `0b4a9b27` sits on the critical path of two other repositories and should be done first, before anything else in this document.

Bind the schema by subtree, not by second parent.
The data commit's tree becomes `{value/, schema/}`: the value under `value/`, the schema content under `schema/`, and the `Schema:` trailer kept as provenance naming the schema commit.
Reachability, gc-safety, and fetch-completeness all follow from tree reachability; `git diff` between two data commits shows schema changes inline; and the commit graph stays pure data history, so `git log`, bisect, and — critically — the merge-base computation `git-forge` `1f25493d` depends on never traverse schema commits.
The second-parent design would have contaminated that merge-base, because schema binding today is a `Schema:` trailer naming a schema commit and the schema ref is itself a commit chain (`store.rs:97,144`).

This makes `0b4a9b27` format-breaking, so it lands in the Wave 1 window rather than Wave 2.
Reachability is still what shrinks `git-forge` `22b36108` from "ship transport that moves two namespaces in lockstep" to "ship transport", and data still becomes self-contained under any refspec.
The multi-parent `commit_forward` entry point the second-parent design required is still needed, but only for `1f25493d`'s merge commits.

| `git-forge` | `d87da1ce` | M | Publish `StoredIssue` and `StoredReview` schemas, and call `put_schema` only when the tree differs; `id` stays commit-derived and unstored.
| `git-query` | `49e0324a` | S | Add `language_version: u32` to `RuleModuleRecord`.
|===

`git-store` `8d109650` is the largest item here and the reason the window exists.
Changing a task's `priority` from `Low` to `High` currently produces an empty `git diff`, an empty `git log --stat`, and no entry in `git ls-tree -r`, because unit-like values encode as empty trees and Git's tooling is blob-oriented.
The central pitch is that Git's own tools are the query language; today they cannot see enums, options, or nulls at all.

`git-query` `49e0324a` is `invisible` and cheap now, unaddable later without a migration.
`git-forge` `d87da1ce` is also required for the merge demo: per-write republication makes `refs/schema/issue` diverge between clones.

On `d87da1ce`: the `Issue`/`StoredIssue` split has a legitimate cause — `id` is derived from the genesis commit, so it cannot appear in that commit's own tree.
The resolution is not to store the id but to name the layering: identity is the address.
`StoredIssue` stays id-less; the entity's identity is the genesis commit oid and its address is `refs/forge/issue/<id>`, one source of truth that nothing stored can contradict.
Publishing `StoredIssue`'s schema then makes the published contract exactly match the disk, which dissolves the mismatch rather than papering over it.
`Issue { id, ..StoredIssue }` is hydration — `load` fills `id` from the ref, as the code already does; if the layering should be visible in the types, a wrapper such as `Loaded<T> { id, value }` generalizes it to `Review` and every future kind for free.
This buys an invariant worth a slide: every commit on an entity ref is a complete, schema-valid value of its kind, and `git log -p` is a pure field-level audit trail with no synthetic revisions, ever.
The precedent is git itself: a commit does not contain its own oid, and you never miss it, because everything that hands you the object also hands you its name.

`git-anchor` `17ceddc9` has little value on its own; its value is being the migration window `0118e93d` and the `context` half of `7c0a7cfd` both need.

=== Across the family: a review that blocks a push

Promoted from "not before the talk": the claims chain is the only sequence in the set that makes the four projects into one system, and the spot check found the receiving half already built.
Five `git-query` predicates are fully implemented against `refs/meta/claims/*` (`gix-query-host/claim.rs`), so `git-query` requires zero changes.
`Review` needs no `verdict` field — `review new` writes one claim commit to `refs/meta/claims/` with `Kind:`, `Target:`, `Signer:`, and `Verdict:` trailers, and the predicates read only trailers.
`approved_by` additionally needs `member/1`, which stays empty until `456fee55` populates `refs/meta/members/*`.

The chain is `94c80ae5` (Wave 1) → `456fee55` → `e25192e7` → `046b3ecf` → `47bc3643`.
It ends with a `pre-receive` hook that refuses a push because a review stored in the repository has no approving verdict from a member declared in the repository, decided by Datalog rules that are themselves repository data.
That is the talk.

== After the conference

Two directions worth stating in the talk as roadmap, not building now.

*Schema-derived EDB.*
A mechanical kind-to-relation mapping, so `git-query` reads any published `git-store` kind without a per-product adapter.
This is what the published-contract rule buys: the moment `git-anchor` publishes `Note`, its anchors become queryable with no new host code.

*Comments become anchors.*
Generalize the anchor target from a positioned blob to any object, then resolve `8990ad01` by delegation and delete `git-forge`'s `CommentEdit`.
Stated honestly, this moves forge-discussion volume onto `b1c4e009`'s scaling answer, so that answer has to hold at forge scale, not just annotation scale.

== Verdicts

All four core ideas are sound.
Each review found one decision that is better than it is currently presented.

[cols="1,4", options="header"]
|===
| Repository | The decision that is undersold

| `git-store` | Every data commit pins the exact schema commit it validated against, so old data stays readable after a kind evolves. This is the answer to the hardest question in schema-on-a-datastore and it is a README bullet.
| `git-anchor` | Embedding the anchored blob under its own oid makes retention free by content addressing, and projection as a two-point tree diff rather than a blame walk works backwards and across unrelated history.
| `git-query` | The dependency policy behind the nine crates is enforced structurally: `gix-query-eval` and `gix-query-check` genuinely have no git dependency. That is stronger and more checkable than the "frozen seam" language used for it.
| `git-forge` | Ids derived from the creation commit are stable across edits while the tip advances, so cross-references do not rot and resolution is one ref read. With the field-per-blob layout, `git log -p refs/forge/issue/<id>` is a field-level audit trail from stock Git.
|===

== Method

Four repository orchestrators, one per repository, each reading the code directly, building it, and driving it against scratch repositories under `/tmp`.
No repository under review was modified.
Effort and impact estimates were produced in a second pass that re-read every filed issue and checked the cited code to judge how contained each recommended fix is.

Sub-agent delegation was requested for the exploration phase and was not available in the environment, so exploration was not parallelised.
At 3,000 to 20,000 lines per repository this cost breadth in `gix-query-host` and in the `gix-query-eval` rewrite internals, and nowhere else that shows in the findings.

Amended 2026-07-28 by a second reviewer (`claude-fable-5`) that cloned all four repositories and spot-checked the load-bearing claims.
Three corrections were folded in: `facet-git-tree` already has `RawTree`, so the missing primitive is only `RawBlob`; the encoding layer is already shared through `facet_git_tree::serialize_into`, narrowing the composition diagnosis to unpublished contracts; and the `Issue`/`StoredIssue` split has a legitimate cause in the commit-derived `id`.
